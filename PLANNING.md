# Orbit — Project Plan

> Your AI work companion — asks questions, calls APIs, delivers insights.

**Last updated: 2026-05-18** — Major revisions from team review.

---

## 1. What is Orbit?

Orbit is an enterprise AI agent built on OpenClaw. It serves as an **intelligent workflow router and executor** — understanding what employees need, calling the right APIs or colleagues, and delivering results in the right format.

Unlike a generic chatbot, Orbit is tailored to your company's systems, APIs, and people — connecting questions to answers, requests to approvers, and problems to owners.

---

## 2. Core Problem We Solve

Enterprise employees lose hours every week on:

- **Routing** — "Who do I ask about this?" / "Where does this request go?"
- **Chasing** — Waiting hours for someone to approve, respond, or provide info
- **Gathering** — Manually pulling data from multiple systems to answer one question
- **Repetition** — Answering the same questions from different people repeatedly

**Orbit handles the routing, the chasing, and the gathering — so people can focus on the work that actually needs them.**

---

## 3. Design Principles

1. **Human always in the loop** — Orbit never acts without the right person's knowledge or approval
2. **Natural language first** — Employees describe what they need, not which system to use
3. **Structured knowledge over blind RAG** — Company knowledge is codified as Skills, not free-text chunks
4. **Zero learning curve** — If you can chat, you can use Orbit
5. **Output adapts to need** — Data → Dashboard. List → Table. File → Download. Approval → Notification.

## 4. Knowledge Architecture: Skills + RAG

### 4.1 The Problem with Traditional RAG

Pure RAG (Confluence + vector search) on procedural knowledge fails because:

- It retrieves by text similarity, not by step sequence
- It cannot distinguish primary steps from secondary details
- Cross-document procedures get mangled ("Step 2 from Doc A, Step 5 from Doc C — but they conflict")

### 4.2 Our Approach: Structured Skills as the Knowledge Unit

We treat **Skills** as both **executable workflows** and **high-quality knowledge units**.

Each Skill has a fixed schema:

```yaml
name: deploy-to-production
trigger:
  patterns:
    - "发布流程"
    - "how to deploy to prod"
    - "deploy to production"
  intent: procedure_execution

steps:
  - id: 1
    description: "Code review completed"
    action: check_status
    api: jira
    parameters:
      ticket: "{{ticket_id}}"
    reads: true

  - id: 2
    description: "Requires QA sign-off"
    action: request_approval
    approval_required: true
    approver_role: qa_team
    reads: false

  - id: 3
    description: "Execute deployment"
    action: deploy
    api: ci_cd
    reads: false
    retry: 3

fields:
  - name: ticket_id
    type: string
    required: true
    human_filled: true
    description: "Jira ticket ID"

dependencies:
  - from: 1
    to: 2
    condition: "status == approved"
  - from: 2
    to: 3
    condition: "approval == granted"
```

### 4.3 Why Skills + RAG Works Together

| Layer | Role |
|-------|------|
| **RAG (routing)** | Fast, lightweight layer that routes user questions to the right Skill |
| **Skills (knowledge)** | Structured, validated knowledge with explicit step relationships |
| **Skills (execution)** | Executable steps with clear read/write/approval semantics |

RAG is the **router**, not just the retriever. It decides: "Is this a factual lookup? A procedural question? A request that needs approval?"

### 4.4 Who Writes the Skills?

Skills are **generated by LLM** from existing documentation, then **filled by humans** with company-specific values.

```
LLM generates Skill skeleton (fixed format)
├── trigger patterns → LLM generates, human fine-tunes
├── steps and dependencies → LLM generates
└── fields → LLM marks slots, HUMAN_FILLED

Human fills in:
├── specific approver names
├── specific channel IDs
├── thresholds and parameters
└── API endpoints and credentials
```

This reduces Skill authoring to "filling in blanks" — not writing from scratch.

## 5. Two Types of Knowledge

We explicitly separate two types of company knowledge, handled differently:

### Type A: Procedural / Guideline Knowledge (High Accuracy Required)

**Characteristics:** Step sequence matters. One wrong step causes failure. Examples: deployment processes, rollback procedures, incident response runbooks.

**Approach:**
- Stored as **Skills with explicit step dependencies**
- Query routes to Skill → returns ordered steps (not similar text chunks)
- Cross-document procedures are rebuilt as a **Process Graph** with declared dependencies
- Uncertain steps are flagged, not guessed

### Type B: Fragmented / Conversational Knowledge (Key Information Extraction)

**Characteristics:** Order doesn't matter. Need to extract key points from many碎片. Examples: meeting decisions, Slack threads, temporary handling notes.

**Approach:**
- Each fragment is pre-processed: extract key entities (who, what, decision, impact)
- Query: aggregate from multiple fragments → synthesize answer
- More tolerant of incomplete information (doesn't need full context)

## 6. The Three Core Capabilities

### 6.1 Ask → Get Answer

User asks a question in natural language. Orbit determines:
- Is this answerable by a Skill? → Execute Skill, return structured answer
- Is this a lookup in a database? → Call API, format result
- Does this need input from a colleague? → Route to the right person

### 6.2 Request → Get Approval

When a task requires human authorization (approval, sign-off, judgment):

```
User requests: "I need database access for this project"
    ↓
Orbit identifies required approver(s) from Skill definition
    ↓
Approval request sent to approver in their channel (WeChat / Slack / etc.)
    ↓
Approver approves or rejects with one click
    ↓
Orbit continues execution or notifies requester of outcome
```

Approval is always **in-channel** — no separate portal, no separate app. Just a message in WeChat that you tap to approve/reject.

### 6.3 Notify → Stay in the Loop

When relevant things happen (your approval is needed, a request you made has been acted on, etc.):

- Orbit proactively notifies the right person
- Message includes context: what happened, what's needed, what happens next
- One-tap actions where possible: "Approve" / "Reject" / "Learn More"

## 8. Security Model

Orbit acts with **the employee's own permissions** — nothing more.

| Mechanism | How it works |
|-----------|-------------|
| **Authentication** | Okta PKCE OAuth — employee authorizes Orbit once |
| **Credential Helper** | Orbit uses a helper script to obtain short-lived tokens from Okta on demand. Long-lived tokens are never stored. |
| **Permission Boundary** | API calls use the employee's Okta token. If the employee can't access something, Orbit can't either. |
| **Approval Gate** | Write/execute operations always require explicit human approval. Orbit never bypasses. |
| **Execution Audit Log** | Every action is logged: who triggered it, what was executed, what was returned. |
| **Emergency Stop** | Any user can halt a running workflow at any time. |
| **Error Pause** | If an API returns an error, Orbit pauses and asks for instructions instead of retrying blindly. |

## 9. Development Phases

### Phase 0 — Foundation (Week 1)
**Goal:** End-to-end demo with one real API (Jira), Okta auth, and formatted output

- [ ] Set up OpenClaw skill structure for Orbit
- [ ] Implement Okta Auth Skill (PKCE flow, Credential Helper)
- [ ] Implement Jira API Skill (read tickets, search, status)
- [ ] Basic JSON → formatted table output (WeChat)
- [ ] Run full flow: WeChat → Orbit → Jira → formatted response

**Deliverable:** "Show me open VOU tickets" returns a formatted table in WeChat.

---

### Phase 1 — Multi-Channel & Routing (Week 2–3)
**Goal:** Route questions to the right Skill or person

- [ ] Implement Router Skill: intent classification → Skill or human routing
- [ ] In-channel approval/reject mechanism (approve/reject buttons in WeChat)
- [ ] Notification Skill: proactive alerts when approvals are needed
- [ ] Skill manifest: registry of all company Skills

**Deliverable:** A request that needs approval triggers a WeChat message to the approver. They approve/reject in chat. Requester gets the result.

---

### Phase 2 — Output Variety (Week 4–5)
**Goal:** Multiple output formats based on data type

- [ ] CSV / Excel export (for list/table data)
- [ ] HTML Dashboard generation (for metrics/time-series using Chart.js)
- [ ] Intelligent format selection (small list → table, time-series → chart, large data → CSV)
- [ ] Handle paginated APIs correctly

**Deliverable:** Employee asks for data and gets the right format automatically.

---

### Phase 3 — Skills Authoring & RAG Integration (Week 6–8)
**Goal:** Company knowledge codified as Skills; RAG as intelligent router

- [ ] Skill authoring template: LLM generates skeleton, human fills fields
- [ ] Skill library: company Skills with version control
- [ ] RAG-as-Router: fast question → route to best Skill (not blind retrieval)
- [ ] Process Graph for Type A knowledge (ordered steps with dependencies)
- [ ] Fragment summarization for Type B knowledge

**Deliverable:** Admins can create new Skills by describing the workflow and filling in company-specific values. RAG routes incoming questions to the right Skill.

---

### Phase 4 — Agentic Workflow Execution (Week 9–12)
**Goal:** Orbit can execute multi-step workflows on behalf of employees (with human approval gates)

- [ ] Execute Skill steps in sequence
- [ ] Approval pause/resume mechanism at designated steps
- [ ] Parallel approval requests (notify multiple approvers at once)
- [ ] Error handling: pause on error, ask for instruction, don't blindly retry
- [ ] Execution status: "Your request is at Step 3 of 5, waiting for DBA approval"

**Deliverable:** "Help me onboard a new employee" → Orbit executes the full workflow (account creation, permissions,通知) with approval gates at the right steps.

---

### Phase 5 — Polish & Enterprise (Week 13+)
**Goal:** Production-ready for company-wide rollout

- [ ] Admin panel: which APIs / Skills each team can access
- [ ] Audit logging dashboard
- [ ] Rate limiting and cost controls
- [ ] User skill sharing: employees can publish personal Skills to company library
- [ ] Mobile-optimized output rendering

## 10. Skill Types

| Type | Owner | Examples |
|------|-------|----------|
| **System Skill** | Core team | Okta Auth, Router, Output Renderer, Approval Workflow |
| **Company Skill** | IT / Admin | Jira, Confluence, AWS Cost, Monitoring APIs |
| **Domain Skill** | Team leads | Team-specific workflows, department processes |
| **Personal Skill** | Individual | Personal FAQ, preferred templates, shortcuts |

**Skill lifecycle:**
1. Company publishes Skill template (approved for org use)
2. Employee instantiates template with their values
3. Employee can also build and test a personal Skill
4. Good personal Skills can be submitted for review → promoted to Company Skill

---

## 11. Out of Scope (for now)

- Code generation / coding assistant (nice to have later)
- Non-REST APIs (GraphQL, gRPC) — REST only for now
- Acting on employee's behalf without approval (always human-in-the-loop)
- Taking over employee's Slack/WeChat accounts
